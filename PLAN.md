# План выполнения: потоковый скоринг фродовых транзакций

## Согласованные решения и исходное состояние

- Цель: полный вариант задания на 8–10 баллов, включая PostgreSQL и раздел результатов в UI.
- Основа ML-части: код и обученная CPU-модель CatBoost из [репозитория семинара](https://github.com/NikitaMalykhin/mts25_mlops_hw2_real_time_fraud_detection), изучен коммит `41540d91f0cbde0106671d3eb8270403508fade4`. Код семинара берём как исходный пример, исправляем и указываем происхождение в README.
- Локальная контейнерная среда: Docker Desktop для Mac с Apple Silicon. На момент составления плана установлен Homebrew, но команды `docker`, `podman`, `colima` отсутствуют. Компьютер: Apple M3 Pro, 36 ГБ RAM, около 294 ГБ свободного места.
- В текущем Git-репозитории пока нет коммитов и remote; лежат только `TASK.md` и архив `teta-ml-1-2025.zip`.
- В архиве: `train.csv` (786 431 строк, 4 504 положительных метки, около 0,57%), `test.csv` (262 144 строки, 17 входных колонок без метки), `sample_submition.csv`. Пустых CSV-ячеек при проходе по этим двум файлам не обнаружено. Обработку отсутствующих и неизвестных значений всё равно предусмотреть для внешних сообщений.

## Что именно строим

```text
CSV из test.csv → Streamlit UI → Kafka: transactions
                                  ↓
                   scoring-service (подготовка признаков → CatBoost)
                                  ↓
                            Kafka: scores
                                  ↓
                         scores-to-postgres
                                  ↓
                    PostgreSQL: transaction_scores
                                  ↓
                    Streamlit UI: раздел результатов
```

Все сервисы запускает один `docker-compose.yml`. Kafka работает на одном брокере в режиме KRaft; ZooKeeper из семинарского примера для новой сборки не нужен. Для Apple Silicon использовать закреплённый образ Kafka с `linux/arm64`, например `apache/kafka:4.3.1`, после проверки его запуска. PostgreSQL и Python-образы также закрепить по версиям. Опциональный Kafka UI допустим для отладки, но не нужен для проверки задания.

**Контракт входного сообщения `transactions`:** один JSON-объект `{"transaction_id":"<UUID>","data":{...}}`, где `data` содержит 17 колонок `test.csv` с исходными названиями. UI создаёт UUID для каждой строки и отправляет строки по одной; для быстрого теста пользователь выбирает ограничение числа отправляемых строк.

**Контракт выходного сообщения `scores`:** ровно один JSON-объект с полями `transaction_id` (строка), `score` (конечное число от 0 до 1) и `fraud_flag` (целое 0/1). Название топика `scores` соответствует формулировке расширенного задания; семинарское `scoring` заменить во всех компонентах и документации.

**Витрина PostgreSQL:** таблица `transaction_scores` с уникальным `transaction_id`, `score`, `fraud_flag`, временем получения и монотонным ID записи для устойчивой сортировки. Проверка диапазона скора и допустимых значений флага — на уровне приложения и БД. Consumer записывает сообщение транзакцией и подтверждает смещение Kafka только после успешного коммита в БД. При повторной доставке `transaction_id` не создаёт дубликат.

**UI:** две понятные вкладки: отправка CSV и результаты. Кнопка «Посмотреть результаты» запускает запросы к PostgreSQL и показывает последние 10 записей с `fraud_flag = 1` и гистограмму скоров последних 100 транзакций. Пустую базу и отсутствие отмеченных фродовых операций показывать без ошибки. Гистограмма строится по реально полученным скорам, без подмены демонстрационными данными.

## Среда: сначала подготовка Docker Desktop

1. Скачать Docker Desktop **для Apple Silicon** с [официальной страницы установки](https://docs.docker.com/desktop/setup/install/mac-install/), установить в Applications и запустить. Для учебного использования Docker Desktop указан как бесплатный в условиях Docker; соглашение показывается при первом запуске. Compose уже входит в Docker Desktop ([документация](https://docs.docker.com/compose/install/)).
2. Проверить в терминале `docker version`, `docker compose version`, `docker info`. Проверка считается пройденной, когда доступен именно Docker Engine, а не только CLI. Если команда не находится после запуска приложения, проверить добавление Docker CLI в `PATH` по настройкам Docker Desktop.
3. Выделить в Docker Desktop ориентировочно 4 CPU, 8 ГБ RAM и достаточно места для образов и томов; это стартовая настройка для локального стека, уточняется по фактическому потреблению. Проверить свободные порты для Streamlit и, если понадобится, внешнего Kafka listener.
4. После появления `docker compose` выполнять сборку и тестирование в контейнерах. Отдельная установка пакетов Python на macOS для работы сервиса не требуется. Подготовку замороженных признаковых справочников можно запускать одноразовым контейнером из локального архива.

## Этапы разработки

### 1. Зафиксировать проект и входные данные

- Создать структуру `scoring_service/`, `scores_sink/`, `interface/`, `scripts/`, `artifacts/`, `tests/`, `sql/` и корневые `docker-compose.yml`, `README.md`, `.gitignore`.
- В `.gitignore` исключить исходные CSV/ZIP, `.env`, виртуальные окружения, кэши, логи и локальные тома. Не отправлять архив соревнования на GitHub. В репозиторий включить маленький синтетический CSV с теми же 17 колонками для автономной проверки формы и контракта.
- Зафиксировать точный список входных колонок и типы, отдельно от схемы выходного сообщения. Указывать в README источник данных и ссылку на семинарскую основу.

**Проверка:** чистый `git status` после первого коммита не показывает датасет, секреты и тома; тестовый CSV проходит валидатор схемы.

### 2. Сделать модель автономной на этапе inference

- Перенести `my_catboost.cbm` и нужные идеи из `preprocessing.py`/`scorer.py` семинара. Модель загружать один раз при старте сервиса, предсказывать только на CPU.
- Написать одноразовый `scripts/export_preprocessor.py`, который читает `train.csv` **вне рабочего сервиса** и сохраняет компактный артефакт: отображения категорий, средние значения для mean encoding, значения для заполнения числовых пропусков, порядок и типы признаков. Учесть точную логику топ-50 категорий, времени, геодистанции и `log1p` из семинара. Сохранить версию артефакта и контрольные данные о совместимости с моделью.
- В контейнер скоринга включать модель и готовый артефакт, а не весь `train.csv`. Скрипт инференса не обучает модель и не пересчитывает статистики на потоке. Порог `0.98` из семинара вынести в конфигурацию с таким же значением по умолчанию; не заявлять качество модели без отдельной оценки.
- Убрать дублирующий вызов `predict_proba`; проверить состав и порядок признаков, неизвестные категории и отсутствие `NaN` в полях результата.

**Проверка:** совпадение признаков и скоров на контрольных строках со скорингом семинарской моделью при той же подготовке; контейнер стартует без `train.csv`; выход соответствует контракту.

### 3. Потоковый сервис и Kafka

- Написать отдельные модули для валидации/препроцессинга, скоринга и чтения/записи Kafka. Исполняемый `app.py` лишь связывает этапы; это выполняет требование о раздельных скриптах внутри контейнера.
- Создать топики `transactions` и `scores` одноразовым init-сервисом в Compose после готовности брокера. Задать адрес брокера и имена топиков через переменные окружения; не зашивать имя топика в `produce()`.
- Для каждого входного сообщения сохранять `transaction_id`, публиковать один результат и подтверждать входной offset после успешной доставки результата в Kafka. В startup добавить повторы подключения и понятные логи. Некорректные сообщения валидировать и отражать в логах; решение об их пропуске описать в README.

**Проверка:** отправка 10–100 строк формата `test.csv` приводит к тому же числу JSON-объектов в `scores`; у каждого валидный ID, score и flag. Перезапуск scorer не приводит к потере уже подтверждённых сообщений.

### 4. PostgreSQL и consumer результатов

- Добавить контейнер PostgreSQL, именованный том и SQL-инициализацию таблицы. Пароль держать в локальном `.env`/Compose secret-переменной и дать безопасный `.env.example` без настоящего секрета.
- Реализовать отдельный `scores_sink` consumer. Он читает только `scores`, проверяет ровно три нужных поля, вставляет запись идемпотентно по `transaction_id` и подтверждает Kafka offset после транзакции БД.
- Проверить запуск после простоя и повторную доставку: счётчик строк БД равен числу уникальных обработанных ID.

**Проверка:** `SELECT` в PostgreSQL возвращает ID, score и flag из Kafka; повтор одного сообщения не создаёт вторую строку.

### 5. UI для отправки и просмотра результатов

- Доработать Streamlit из семинара: валидировать заголовок CSV, показывать количество строк и прогресс, дать лимит строк для быстрого smoke test, отправлять без искусственной задержки `sleep(0.01)`.
- Добавить раздел результатов и кнопку «Посмотреть результаты». Использовать параметризованные SQL-запросы: последние 10 фродовых строк и последние 100 скоров по порядку поступления. Отображать число записей, дату обновления и пустые состояния.
- Запросы UI выполнять через внутреннее имя сервиса PostgreSQL, сохраняя базу только в сети Compose. Результаты не читать напрямую из Kafka — по заданию они должны приходить из витрины.

**Проверка:** после загрузки CSV видны новые записи; график содержит максимум 100 значений; список содержит максимум 10 строк с `fraud_flag = 1`; при отсутствии таких строк интерфейс работает штатно.

### 6. Compose, инструкции и приемка

- Зафиксировать версии Python-зависимостей, исправив ошибку семинара `confluent-kafka==2.10.0.venv`; Dockerfile разделить по сервисам и сделать воспроизводимыми для `arm64` и обычного `amd64`.
- Добавить healthcheck для Kafka и PostgreSQL и условия `depends_on: service_healthy` / `service_completed_successfully` для зависимых контейнеров. Обычный `depends_on` не гарантирует готовность сервиса ([Docker Docs](https://docs.docker.com/compose/how-tos/startup-order)).
- В README дать последовательность с нуля: установка Docker Desktop, подготовка `.env`, `docker compose up --build -d`, проверка `docker compose ps`, URL UI, загрузка синтетического CSV или первых 100 строк локального `test.csv`, проверка топика и SQL, просмотр логов, остановка. Указать, что полный `test.csv` велик и тестировать сначала малую порцию.
- Сделать автоматические проверки схемы, преобразования признаков, вывода модели и идемпотентной записи; затем прогнать интеграционный сценарий на поднятом Compose. Отдельно проверить CPU-only запуск, пересоздание контейнеров, сохранность PostgreSQL-тома и запуск на чистой копии репозитория без архива датасета.
- После зелёной приемки подготовить коммит(ы), создать GitHub-репозиторий, добавить remote и отправить код, модель и маленький демонстрационный CSV. Проверить публичный README и повторить запуск по нему с чистого клона.

## Критерии готовности

1. `docker compose up --build -d` поднимает Kafka, инициализацию топиков, scoring service, PostgreSQL, scores sink и Streamlit без ручного порядка запуска.
2. Строки `test.csv` превращаются в отдельные сообщения `transactions`, затем в объекты `scores` ровно с тремя требуемыми полями; score реально вычислен CatBoost на CPU.
3. Для каждого уникального результата есть одна запись в PostgreSQL; оба компонента продолжают работу после перезапуска.
4. Кнопка UI показывает последние 10 фродовых записей и гистограмму последних 100 скоров с корректными пустыми состояниями.
5. README позволяет повторить запуск на машине с Docker Desktop; в GitHub нет исходного архива, train/test CSV и секретов.

## Технические риски, которые нужно снять при реализации

- **Совместимость preprocessing с готовой моделью.** Экспортированные справочники должны воспроизводить порядок и типы признаков семинарской модели. Контрольные строки и сравнение скоров обязательны до контейнерной интеграции.
- **Apple Silicon и Kafka.** Проверить конкретные теги образов на `linux/arm64` и запуск в KRaft на M3; не оставлять плавающие `latest` в сдаваемой Compose-конфигурации. [Apache Kafka Docker](https://kafka.apache.org/43/getting-started/docker/).
- **Дисбаланс классов.** В случайных 100 строках фрод может не встретиться. Это нормальное пустое состояние UI; отдельно проверить SQL-представление положительных результатов на контролируемых тестовых сообщениях, не выдавая их за оценку качества модели.
- **Повторы Kafka.** Для локального задания достаточно доставки с возможными повторами и идемпотентной записи; уникальный `transaction_id` защищает витрину от дублей.

Пункты выше используются как чек-лист приёмки готового проекта.
